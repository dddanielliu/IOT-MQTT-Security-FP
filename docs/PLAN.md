# 實驗計畫（草稿）

狀態：討論中，尚未定案。以下是可能的實驗方向，不是最終分工。

## 研究問題

在既有的 Mosquitto + sensor + controller 架構上加入防護，比較前後，**攻擊者送出的訊息中，實際被 controller 採納的比例是否下降**？代價（誤報、延遲）是多少？

## 前提

- 防守方不知道誰被攻破，所有 client 以相同規則檢查，不預設身份。
- 評估用的 ground truth 由攻擊腳本記錄（每則訊息是否為攻擊、來源為何），只給評估使用，防護端看不到。
- 攻擊者假設：已通過認證、符合 ACL 的合法 client 被攻破（可能拿到密碼）。

## 指標

| 指標 | 定義 |
|---|---|
| ASR（攻擊成功率） | 被 controller 採納的攻擊訊息數 ÷ 攻擊訊息總數 |
| 攔截率 | 1 − ASR，依攻擊類型分開報告 |
| 誤報率（FPR） | 正常訊息中被錯誤拒絕的比例 |
| 偵測延遲 | 攻擊開始到黑名單生效的時間，以及期間漏掉的訊息數 |
| 額外開銷 | 防護層增加的端到端延遲 |

## 攻擊樣本（候選）

1. 超出範圍的假值
2. 相對上一筆跳變的假值
3. 洪水式發布
4. 重複或重放同一則訊息
5. 在合理範圍內慢慢漂移（預期防護擋不住，作為殘留風險）

## 防護設定（ablation，前後比較）

| 設定 | 內容 |
|---|---|
| A0 基準 | 現況：密碼 + ACL |
| A1 | + 數值合理性（範圍、變化率） |
| A2 | + 速率與重複/重放偵測 |
| A3 | + 黑名單（違規分數超過門檻則隔離，有時效） |

同一組攻擊腳本、同一組正常流量，每種設定重複多次取平均。

## 實作位置（待決定）

- **方案 1：Mosquitto 外掛（broker 端）。** 最貼近既有架構。前提：外掛能否讀取 payload 並阻止轉發，需先做可行性測試。頻率與重複偵測只需要 metadata，比較容易。
- **方案 2：broker 前的 proxy。** 若外掛無法讀取 payload，退一步使用此方案，架構只多一個節點。
- **方案 3：controller 端檢查。** 最簡單，但屬於事後偵測，無法量測攔截率，只作為對照。

黑名單的實作：優先考慮 Mosquitto dynamic-security 外掛；若不可行，在 Guard 內丟棄該 client 的訊息。

## 正常流量設計

- 不要讓 sensor 送出過於規律的固定值，否則偵測太容易，結果不具說服力。
- 加入抖動、偶發的合理突波，用來量測誤報率。

## 偵測機制（候選）

每個 client 的每則訊息都經過同樣的檢查，每項命中會加分，分數超過門檻就隔離。

| 編號 | 機制 | 判斷依據 | 需要的資料 | 對應攻擊 | 所屬設定 |
|---|---|---|---|---|---|
| D1 | 發布速率異常 | 滑動視窗內的訊息數超過門檻 | client ID、時間戳（metadata） | 洪水 | A2 |
| D2 | 重複與重放 | seq 未遞增、或 payload 雜湊在視窗內重複 | payload 內的 seq 或雜湊 | 重放、重複 | A2 |
| D3 | 發布間隔偏離 | 間隔與 sensor 預設週期的差距過大 | 時間戳 | 洪水、靜默（心跳遺失） | A2（選做） |
| D4 | 數值範圍 | 值落在該 topic 的物理範圍內 | payload 的 value | 超範圍假值 | A1 |
| D5 | 變化率 | `|v − v_prev| / Δt` 不超過最大斜率 | payload 的 value 與 ts | 跳變假值 | A1 |
| D6 | 統計偏離（延伸） | 與 warm-up 期間的均值、標準差相比的 z-score | 正常流量的統計 | 部分漂移 | 延伸，不一定做 |
| D7 | 探測（ACL 拒絕） | 單一 client 在視窗內的 ACL 拒絕次數超過門檻（例如試圖發到未授權 topic） | broker 的 ACL 拒絕事件 | 偵察、越權嘗試 | A2 |
| D8 | 訂閱模式異常 | client 突然訂閱萬用字元（`#`、`+`），或訂閱其 ACL 範圍外的 topic（若 ACL 已擋則計入 D7） | SUBSCRIBE 事件與該 client 的正常訂閱清單 | 偵察、竊聽準備 | A2 |

### 分數與隔離（草案）

- 每個機制命中加一個固定分數（例如 D1、D2 各 2 分，D4、D5 各 1 分），分數會隨時間衰減。
- 分數超過門檻 → 隔離該 client，丟棄其訊息並記錄事件。
- 隔離時效：例如 60 秒後自動解除，再次違規則加倍時效。
- 具體的分數、門檻與時效數字待實驗前決定，並在 A3 中調整。

### 依賴與注意事項

- **payload 格式要先定義。** 建議統一為 `{"value": ..., "seq": ..., "ts": ...}`。D2、D4、D5 都依賴這三個欄位，缺一不可。
- **D1、D2、D3 只需要 metadata 或 seq，比較容易在 broker 端實作。** D4、D5 需要讀 payload，取決於實作位置的可行性測試。
- **D6 不列入第一版**，除非前面幾項都完成且時間足夠。
- **D7、D8 的判斷是「相對於 ACL 的預期」。** 每個 client 的合法 topic 範圍由 ACL 定義，不需要學習，所以不會有 warm-up 的問題。
- **D7、D8 抓不到的情況：** 攻擊者只在合法的 topic 範圍內活動（例如只用被攻破 sensor 自己的 topic），這種行為要靠 D1 到 D5 判斷。這也是殘留風險的一部分，要寫進報告。

## 殘留風險（需誠實寫入報告）

- 在 profile 範圍內慢慢漂移的假值，分數不會超過門檻。
- 攻擊者在 warm-up 期間已經得手，profile 會把攻擊當成正常。
- 偵測有延遲，黑名單生效前的攻擊訊息會漏掉。
